中文文案是怎样进入收集结果的？

本套新课从一次真实的 Webpack Loader 调用开始，沿着源码、提取器、snapshot、Session、Plugin 和输出文件走完一条链。目标不是记 API，而是能解释任意一段中文最终为什么被收集，或为什么没有被收集。

1. 先记住两层调用链

直接资源请求（JS / CSS / HTML） ↓ myloader.pitch(loaderContext) ↓ 读取当前资源的原始源码 runCollect(loaderContext, sourceText) ↓ Resource 归类 → include/exclude → extractor 分派 collectedFor(resource, sourceText, config) ↓ extractScript / extractHtml / extractCss ↓ 返回 entries snapshotFor(resource, entries) ↓ record(loaderContext, config, included, snapshot) ├─ 写入 module.buildInfo.i18nCollect └─ 提交当前 Compilation 的 Session round Vue SFC 的额外层级： App.vue → vue-loader 解析并创建 block 子请求 ├─ App.vue?vue&type=script ├─ App.vue?vue&type=template └─ App.vue?vue&type=style&index=0 ↓ 每个子请求各自进入上面的 myloader.pitch 链 Webpack 完成编译 ↓ MyI18nPlugin.done ↓ 汇总 snapshot → buildCatalog → writeOutputs 语言词典、source map、源语言 catalog、catalog metadata

这里的 Webpack request 指一次具体的 Loader 请求。Vue 的根 App.vue 请求先由 vue-loader 拆出 block 子请求，myloader 再参与这些子请求。图中的 JS / Vue / CSS / HTML 分支是多个独立请求的概念图，不是一次 myloader.pitch 在内存中同时分叉执行。

最关键的边界是：Loader 负责发现一份资源里的文案，Plugin 负责把多份资源的发现结果合成并发布。Plugin 不扫描 src，也不重新解析业务源码。

2. Webpack 什么时候调用 Loader

项目导出的是 myloader。Webpack 为每个模块请求创建 Loader Context，并把当前资源路径、query、所属 Module、Compilation 等信息放到 this 上。

src/message.js
  └─ module request
     └─ i18n-collect/myloader
        └─ loaderContext.resourcePath = .../src/message.js
           loaderContext.resourceQuery = ''
           loaderContext.rootContext = project root

Loader 有两个入口阶段：

  1. pitch：先用 fs.readFileSync(this.resourcePath, 'utf8') 读取磁盘上的原始源码并收集。
  2. 普通 Loader 函数：如果 pitch 已经收集，就只透明传递；如果特殊链路没有执行 pitch，才用收到的 source 作后备收集。

this.data.collected 只属于这一次 Loader 请求，用于防止 pitch 和普通阶段重复收集。它不是跨构建的持久状态。

3. Vue 为什么看起来先经过 vue-loader？

要分开看根 SFC 请求与 block 子请求。Webpack 先构建根 App.vue 请求；vue-loader 在该请求的 Loader 生命周期中解析 SFC，并让生成的组件模块依赖多个新请求：

根请求：App.vue
  ↓ vue-loader 解析 SFC
子请求：App.vue?vue&type=script
       App.vue?vue&type=template
       App.vue?vue&type=style&index=0

Webpack 会把每个子请求当成独立模块，再为它匹配各自的 Loader 链。myloader 配置在这些子请求上，所以“vue-loader 先、myloader.pitch 后”描述的是不同 request 的递归构建顺序，不是同一条 Loader 链中 normal 阶段插队到 pitch 前面。

对于同一个 request，最终 Loader 列表永远遵循：

配置列表：A → B → C
pitch：   A.pitch() → B.pitch() → C.pitch()
normal：  C()       → B()       → A()

enforce: 'pre'、普通规则和 enforce: 'post' 会先影响 Webpack 组成最终列表的顺序；它们不会增加新的执行阶段。最终列表确定后，仍是从左到右执行 pitch、从右到左执行 normal。

对 Vue block，resourcePath 仍是完整的 App.vue，而 resourceQuery 指出 script、template 或第几个 style。正常收集时，myloader.pitch 主动读磁盘中的原始 App.vue；它不会自动收到 vue-loader 的转换结果。若 pitch 没有完成收集，normal 阶段的后备路径可能拿到被当前 block 链中后续 Loader 改写的 source，因此 Vue 收集会重新读取完整原始 SFC 并按 query 定位 block，以保持原始位置准确。

4. runCollect 的八个动作

顺序实现目的
1检查 thread-loader收集必须在主进程运行，因为要访问主 Compilation/Session。
2loadConfig + trackConfig读取配置，并让配置文件成为 Webpack dependency。
3canonicalPair + describeResource得到项目相对路径、block、lang、style index 和 identity。
4isResourceIncluded先看 include，再由 exclude 最终否决。
5collectedFor把 script、template、html、style 分派给正确 extractor。
6snapshotFor把本资源的完整结果包装成可替换的 snapshot。
7record同时写 Module metadata，并提交当前 round。
8callback(null, source, sourceMap, meta)保持源码、source map 和 meta 不变，避免影响 bundle。

即使资源没有中文、被 scope 排除，或产生空结果，也要留下 Loader invocation 证据。否则 Plugin 无法区分“确实没有文案”和“Loader 根本没有接入”。

5. 一个最小例子

// src/message.js
const title = "首页"
const hint = "Loading"

对这个 JS Module，extractScript 用 Babel 解析 AST：

  • "首页" 是 StringLiteral，包含 Han 字符，生成一个 script-string entry。
  • "Loading" 不含 Han 字符，不生成 entry。
  • 解析只观察 AST，不执行代码、不求变量值、不做常量折叠。
  • entry 带着值和 source location 进入 snapshot；原始 JS 仍原样传给后续 Loader。

之后 Plugin 才会把它聚合成兼容的 MD5 dictionary，并在有 key 时把它放入 keyed source catalog。收集阶段不会把代码改成 t('...')。

检索练习

文件 src/a.js 中有 const x = "你好"，但它没有进入 Webpack 的 myloader 链。Plugin 是否应该通过扫描磁盘把它补回来？如果 Loader 运行了但文件只有英文，又应当留下什么证据？

不应该补扫。Loader 是唯一的源码收集入口，未进入链的资源应暴露为集成配置问题。若 Loader 已运行但没有中文，仍应记录 invocation，并提交空 snapshot（或被排除时记录 excluded metadata）；这样 Plugin 能区分“空结果”和“没有接入”。

本课结论：中文从源码到正式输出不是一次扫描，而是“Loader 观察单个资源 → Snapshot 进入构建状态 → Plugin 在成功编译后聚合发布”的流水线。
