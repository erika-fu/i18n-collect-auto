翻译：草稿、审阅状态与明确授权

目标：用 planTranslation / applyDrafts 推导目标 catalog 如何变化，并理解为什么不会盲目覆盖译文。

输入与 provider 契约

translate.js 要求已有源 catalog 和对齐的 v1 metadata，并加载项目内 translationProvider。provider 是函数或导出 translate 的模块：

{
  sourceLocale: 'zh', locales: ['en'],
  items: [{ key: 'home.title', source: '首页', locales: ['en'] }]
}
→ { drafts: [{ key: 'home.title', locale: 'en', text: 'Home' }], failures: [] }

未请求 pair 的输出被忽略；请求 pair 既无 draft 也无 failure 则是 provider returned no draft。失败记录优先于同一 pair 的 draft。

纯状态机先计划，后应用

mycommon/translate.js 保持文件 I/O 之外的逻辑可测试：

目标项状态默认计划state 结果
key 缺失请求 provider成功草稿写入，记录当前 source fingerprint。
已有文本，未 --retranslate保留，不请求无记录时接纳为 current；指纹不同则 needs-review。
已有文本，--retranslate请求 provider成功时替换并设 current；失败时保留原文本/审阅状态。

空字符串也是“已有翻译”；只有缺少 key 才是未翻译。该细节防止合法的空文案被反复覆盖。

partial 与 strict

partial（默认）提交所有成功 drafts 和本轮 review 变化，保留失败 pair，最终退出 4；strict 只要一个 pair 失败就提交零变化、报告 withheld drafts 并退出 4。两者都不是 storage failure。

网络授权不是形式

provider 函数或模块标记 network: true 时，命令在将源文本交给它之前必须获得许可：交互 TTY 显式确认，或使用 --allow-network；CI/非交互输入不能用管道“回答”。拒绝时退出 5，写入为零。无待翻译项不提示也不调用 provider。

提交范围

目标 catalog 与 translation-state.json 作为本轮改变集一起 journal 提交。下一次 translate 先恢复发现的残留 journal；无法恢复是 storage failure（6），而不是把半写入当正常输入。

检索练习

源文本 fingerprint 变了，但目标 en.json 中已有翻译，未传 --retranslate。系统为什么保留翻译而不自动请求 provider？

现有译文可能是人工校对、术语化或有业务语境的结果。自动覆盖会丢失人工价值；保留文本并标记 needs-review 把判断交给人，同时用旧 fingerprint 记录“它曾针对哪个源文本被接受”。
