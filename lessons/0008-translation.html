翻译：先计划，再应用草稿

本课追踪一个 source key 在目标目录中从缺失、待审阅到 current 的状态变化，并解释 provider 为什么只返回 drafts。

1. translate 的输入不是 hash map

translate.js 读取 source catalog 和 version 2 catalog.meta.json；旧 version 1 metadata 会先升级。它按 localization key 对齐 source text 与 fingerprint，并读取已有目标目录和 translation-state.json。自动 key 的身份已经由 collection history 决定，translate 不会再按文案值或 MD5 重新合并 occurrence。

source catalog：{ "src.pages.Order.8f31a2c4": "保存" }
metadata：same key → sourceFingerprint: a1b2...
en.json：{ "src.pages.Order.8f31a2c4": "Save" }
state：en/same key → { sourceFingerprint: a1b2..., review: "current" }

如果 source catalog 和 metadata 无法按相同 key 对齐，命令不能安全翻译；这不是“少一行提示”，而是输入版本不一致。

2. provider 契约：输入 item，输出 drafts/failures

provider 得到的是待处理的语义项，不是整个源码文件：

{
  sourceLocale: 'zh',
  locales: ['en'],
  items: [{ key: 'home.title', source: '首页', locales: ['en'] }]
}

→ {
  drafts: [{ key: 'home.title', locale: 'en', text: 'Home' }],
  failures: []
}

applyDrafts 只接受本轮 pending pair；未请求的 key/locale 输出会被忽略。一个 pending pair 既没有 draft 也没有有效 failure，会被补成 provider returned no draft。同一 pair 同时出现 failure 和 draft 时，failure 优先，避免不确定的结果被写入。

3. planTranslation 如何决定 pending

目标状态没有 --retranslate有 --retranslate
key 不存在加入 pending，请 provider 翻译加入 pending
key 已有文本保留，不请求加入 pending，成功后替换
已有文本但 fingerprint 不同保留并标记 needs-review请求新 draft
已有值是空字符串仍算“已存在”只有 retranslate 才请求

“存在”用的是 own-property 判断，不是 truthiness。空译文可能是业务上合法的有意空值，不能被误判成缺失而反复请求。

4. 为什么源文案变化不自动覆盖人工译文

假设原来：

home.title → source “首页” → en “Home” → current

后来 source 改为“主页”。系统会保留 en: "Home"，但将 review 改为 needs-review，因为旧译文可能已经人工校对、采用产品术语或有上下文约束。它记录旧 fingerprint，明确表示“这份翻译是针对旧源文案被接受的”。是否重新翻译由人通过 --retranslate 决定。

5. partial 和 strict 是提交策略

两种策略都可能得到 provider failures，但写入范围不同：

pending pairs → applyDrafts ↓ partial：成功 drafts + review changes 写入；失败 pair 保留；退出码 4 strict：只要有 failure，所有本轮变化 withheld；退出码 4

strict 的“零变化”只针对本轮翻译提交，不代表 collection 产物也回滚。storage failure 则是另一类问题：journal 恢复失败时，不能把它当普通 provider failure。

6. 网络授权发生在交付 source 前

provider 模块或函数可以标记 network: true。translate 在调用它前检查授权：交互 TTY 中明确确认，或传 --allow-network；非交互环境不能靠管道输入伪造确认。拒绝时不把 source text 交给 provider，不写 target catalog，退出 5。

没有 pending items 时不调用 provider，也不弹网络授权提示。这个顺序避免“其实没有待翻译内容，却要求网络权限”的误导。

7. target catalog 和 state 一起提交

一次成功翻译可能同时修改多个 locale 文件和 translation-state.json。CLI 通过同一套 journal 提交；失败时恢复全部文件。下一次 translate 发现残留 journal，会先恢复，而不是继续基于半写入目录计算计划。

检索练习

已有 en.json[home.title] = "Home"，但 source fingerprint 已变；不传 --retranslate 时，provider 会被调用吗？最终 state 是什么？

不会调用。目标 key 已存在，所以保留“Home”；由于 fingerprint 不同，state 标记为 needs-review。只有显式 --retranslate 才会把该 pair 放入 pending，请 provider 生成新 draft。
