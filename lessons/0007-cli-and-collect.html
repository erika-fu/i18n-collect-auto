CLI：复用管线，而不是绕开管线

目标：知道四个命令的边界，重点理解 collect 如何运行已有 Webpack 集成。

main 是窄分发器

cli/main.js 只识别 collect、translate、replace、run，调各自函数，规范化 stdout/stderr/exit code。命令语义各自独立，不能让 main 变成业务规则中心。

collect 不扫描源码

collect.js 解析 --webpack-config、--include、--exclude、--context-filter、--json，临时设置 scope overrides，随后在项目外临时目录运行项目已配置的 Webpack compiler。

它的价值不是提供第二个 collector，而是把 GUI/watch build 中同一 loader/plugin 契约变成一次可自动化的命令。没有 loader/plugin 集成仍会是 collection failure（2），而不是让 CLI 越权扫描。

为何 collect 阻断网络

收集应是纯本地、可重复的静态分析。collect 包裹单次 webpack run 时阻断 HTTP/HTTPS/socket/fetch 等网络 primitives；这避免用户误以为简单导出源文案会外传。翻译是唯一明确允许项目 provider 接触源文案的阶段，且另有授权门。

report 与失败归类

成功 report 包含 dictionary count 和 catalog 路径，并以 collection 前的 metadata 为基线报告 added/removed/changed/unchanged。分类不能只看 Webpack 的“有 error”：已知 loader/key/integration 等问题是 2；其他 build 错误是 3；配置/参数问题是 1。

run 的编排规则

run.js 先将 flags 路由到其所属 stage。用户即使写成 --replace --collect，也总按 collect → translate → replace 执行；任一阶段非零即停止，--write 仍必须显式传递给 replace。这使每个阶段永远消费前一成功阶段的输入。

检索练习

为什么 npx i18n-collect collect 不承诺让本次生成的 bundle 一定包含本次新字典？

因为 collect 复用普通构建时序：应用在模块构建中读取构建开始时存在的字典，而 Plugin 到 compilation 完成后才聚齐全部文本并写新字典。命令保证磁盘 collection artifacts 最新，不承诺同一 bundle 的字典新鲜度；watch 的下一轮才可消费它。

操作准则：先用 collect --json 验证收集与目录变化；只有它成功后，才考虑翻译或预览替换。
