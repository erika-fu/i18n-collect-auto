CLI：复用构建管线，而不是绕开它

本课沿着 npx i18n-collect collect 的一次执行，区分参数解析、Webpack 运行、report 和退出码。

1. main 为什么故意很薄

cli/main.js 只负责识别命令、设置 cwd 和把结果写到 stdout/stderr。真正的规则在 collect.js、translate.js、replace.js、run.js 中。

argv ↓ main：找 command，调用 stage stage：解析自己的 flags，执行自己的 domain rules ↓ { code, stdout, stderr } ↓ main：统一打印并 process.exitCode

这样 collect 的网络阻断不会污染 translate 的 provider 授权逻辑，replace 的 strict 也不会被 main 偷偷解释成 collect 规则。

2. collect 的输入和边界

collect.js 接受 --cwd、--webpack-config、重复的 --include/--exclude/--context-filter 和 --json。它先读取配置并加载用户指定的 Webpack config；如果导出的 config 是函数，还会先执行函数。

然后它做三件关键的隔离：

  1. 把输出 bundle 重定向到临时目录，避免 collect 污染项目产物；
  2. 关闭 watch 和 cache，保证这是一次可重复的单次 compiler run；
  3. 只通过项目已经配置的 loader/plugin 收集，不递归扫描源码。

所以 collect 不是第二个 extractor。它只是把普通 Webpack 集成从 watch/GUI 场景变成一次 CLI 场景。

3. 为什么 collect 要阻断网络

collect 的契约是“本地静态收集”。它临时替换 http.request、https.request、net.connect、Socket.connect 和可用的 fetch；任何网络尝试都会抛出 build failure。收集结果不会把源文案发送给 provider。

这和 translate 的授权边界不同：只有翻译阶段明确加载 provider，并在 provider 标记 network: true 时请求交互确认或 --allow-network。一个“只导出文案”的命令不应该因为用户项目中的某段构建代码而意外联网。

4. collect 的真实调用路径

parseCollectArgs ↓ setCollectionOverrides（仅 scope 字段） ↓ load 用户 webpack config ↓ redirectEmit + runCompiler ↓ myloader / MyI18nPlugin 正常收集 ↓ 读取 collection 前的 catalog metadata ↓ diffCatalog(previous, next) ↓ humanReport 或 JSON report ↓ clearCollectionOverrides

注意临时 override 只允许 include、exclude、contextFilters。CLI 不应临时改输出路径、parser 或翻译设置来改变 collection 的语义。

5. 退出码不是“有没有 Webpack error”

码类别例子
0成功报告生成；即使 entries 为 0 也可能成功
1configuration未知 flag、缺少 flag value、配置非法
2collectionkey conflict、Loader 未接入、Loader 不在主进程
3build普通 Webpack 编译错误、用户 config 加载错误

分类器会检查错误消息：已知的 i18n-collect failed、integration 和 thread-loader 错误属于 collection；其他构建错误不能被伪装成“收集失败”。

6. run 如何编排阶段

run.js 识别用户选中的 stage，但无论 flags 出现顺序如何，都按：

collect → translate → replace

每个 stage 的专属参数只转发给它；例如 --adapter 没有 --replace 就是 configuration failure。前一阶段非零时立即停止，后续阶段不会消费不完整输入。--write 也必须显式属于 replace，而不会因为选了 run 就自动写源码。

7. 一个重要时序限制

collect 运行的是普通构建：应用模块可能在 compilation 早期读取旧 dictionary，Plugin 在末尾才把新 dictionary 写到磁盘。因此 collect 保证“磁盘上的收集产物是本轮成功结果”，不保证“同一次生成的 bundle 已嵌入这份新 dictionary”。watch 的下一轮才会消费它。

检索练习

用户执行 run --replace --collect --json，但 collect 返回 2。translate 和 replace 会发生吗？为什么？

不会。run 固定按 collect、translate、replace 顺序执行；collect 的非零结果立即停止。JSON report 会包含 run 的失败类别、消息和已经完成的 stage 结果，但不会假装后续阶段成功。

操作准则：先用 collect --json 看 entries、catalog diff 和 failure 分类，再决定是否进入 translate 或 replace。
