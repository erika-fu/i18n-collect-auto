COURSE · 06 / 10 · KEY MODEL

从“文案值”到稳定的翻译 occurrence

本课重新整理 key 的完整生命周期：旧的 MD5 字典如何兼容，新 catalog 如何为每次 occurrence 分配独立身份，以及源码移动、改文案或发生歧义时，系统如何安全地复用或放弃旧 key。

1. 先分清四种身份

身份示例它回答的问题
Resource identitysrc/App.vue::template[lang=html]这次提交替换的是哪一个资源快照？
文案值的 MD5md5("保存")旧的 hash dictionary 中有哪些文本值？
OccurrenceOrder.vue 中某个具体的“保存”源码中是哪一次出现，可以精确定位和替换？
Localization keysrc.pages.Order.8f31a2c4 或 order.save运行时和翻译 catalog 使用哪个稳定翻译单元？
记忆句：Resource identity 认资源，MD5 认文案值，Occurrence 认一次出现，localization key 认翻译身份。相同文本不等于相同翻译单元。

2. 现在仍然有两条输出轨道

CollectionStore 继续按文案值生成 hash collection output；buildCatalog 则为 catalog 中的每个 occurrence 生成或复用 localization key。

源码 occurrence A：“保存"
源码 occurrence B：“保存"

zh_hash.json                 // 兼容旧运行时：按值去重
  md5("保存") → "保存"

catalog/zh.json              // 新运行时：按翻译身份区分
  order.save → "保存"
  toolbar.save → "保存"

因此 MD5 dictionary 可以只有一个“保存”，而 catalog 可以有两个 key。源替换也优先使用 key；尚未迁移的旧调用仍可通过 MD5 compatibility fallback 工作。

这也是为什么不能把 MD5 当作业务 key：它没有表达来源位置、语义意图或“这两次出现是否应该独立翻译”。

3. Automatic key：新 occurrence 先获得独立身份

没有相邻 i18n-key directive 时，代码会调用 automaticKey({ path, kind, value, location })。首次 collection 的 key 形如：

pathSlug + "." + sha256(path, kind, value, start, end).slice(0, 8)

src/pages/Order.vue 中的“保存”  → src.pages.Order.8f31a2c4
同文件中的第二个“保存”      → src.pages.Order.39b7e110
另一个文件中的“保存”        → 另一个独立 key
  • key 的可读前缀只是诊断提示；hash 中包含首次位置，所以同一文件的重复 occurrence 不会在首次 collection 时自动合并。
  • 位置变化后，不能单靠重新计算当前坐标得到稳定身份；稳定性来自上一轮的 catalog metadata。
  • 代码仍导出 deriveKey 作为兼容名称，但它指向当前的 automatic-key 实现；“按 path + kind + value 去重”的旧算法已经不是当前模型。

4. 下一轮 collection 如何复用旧 key

每个 occurrence 的 metadata 记录 semanticHost、childRole、localContext、source location 和稳定 occurrence id。重新 collection 时，matchAutomaticKeys 按以下顺序寻找历史身份：

  1. 先对应 semantic host。 未改变的 host 直接对应；源码文件或语义块安全地一对一移动时，也可以建立 host correspondence。
  2. 再比对 sibling context。 在历史和当前 occurrence 数量相同的组中，唯一的 sibling:0、sibling:1 等 context 可以复用对应 key。
  3. 最后使用 source text。 未匹配的候选只有在历史 occurrence 和当前 occurrence 的文本都唯一时才复用；文本是辅助证据，不是唯一身份。
  4. 无法唯一判断就不猜。 当前 occurrence 获得一个避开所有历史 key 的新 proposed key，并产生 ambiguity report。
上一轮：A“你好”  B“欢迎”
本轮：  X“新增”  A“你好”  B“欢迎”

X → 新 key
A → 复用旧 key
B → 复用旧 key

插入源码行本身不会破坏 A、B 的身份，因为匹配依赖 structural anchor 和历史 metadata，而不是把当前 line/column 当成永久身份。

5. Ambiguity：宁可暂停，也不把译文贴错位置

例如上一轮同一 semantic host 有两个相同的“保存”，本轮变成三个相同 occurrence。任何一个当前片段都可能对应两个历史 key；系统没有足够证据知道哪份译文属于哪一次出现。

当前 occurrence：“保存” at sibling:0
  candidate: old-key-1
  candidate: old-key-2

结果：分配新的 proposed key + 写 ambiguity report + collection round 失败

失败轮次不会发布半成品：上一轮 dictionary、source map 和 catalog 保持不变。开发者可以：

  • 在源码中添加明确的 i18n-key；或
  • 在 catalog metadata 旁的 identity-confirmations.json 中持久化选择的历史 key 或 proposed key。

这不是多余的流程，而是在保护已有译文：错误复用一个 key，通常比生成一个需要重新翻译的新 key 更危险。

6. Explicit key：覆盖自动身份，也可以有意共享

// i18n-key: order.save
buttonText = '保存'

directive 表达的是稳定的业务意图，而不是给当前字符串起一个漂亮别名。多个 occurrence 可以显式共享 order.save，但必须满足相同的 message contract：

同一个 key： “你好，{name}”   ✓
同一个 key： “你好，{user}”   ✗ placeholder contract 不同
同一个 key： “保存”           ✗
             “保存 {count} 个”  message pattern 不同

buildCatalog 会按 key 分组，再按 message contract 分 variants。一个 key 出现不兼容 variants 就是 key conflict；冲突会列出所有相关位置，并在正式输出前失败，不能静默选择第一条文案。

7. Fingerprint 与 occurrence 生命周期

fingerprintOf(source) 是源文案的 SHA-256 前 16 位。它回答“这个 key 的 source text 是否改变”，不回答“这是不是同一个 occurrence”。

事件key / metadata目标译文状态
只移动源码，文本不变通过 history 复用 key；location 更新保持 current
同 occurrence 改成“提交”key 保持；fingerprint changed保留译文，但标记 needs-review
一处 occurrence 消失key 进入 orphaned；metadata 暂留译文暂留，等待退休策略
确认退休或启用 prunekey 从 active metadata 移除，并出现在 removed report下一次 translate 移除目标译文和 review state
相同文本新增到另一处MD5 值不增加；新增 occurrence key可与原位置独立翻译

所以 catalog metadata 不只是 key → source + locations[]，还保存 occurrence identity、来源 origin、状态和审阅所需的 fingerprint。

8. 替换时，key 必须跟着 occurrence 走

替换器不能再“找到文本就全部替换”。它必须读取当前 occurrence 的 location 和 localization key，并检查位置是否 stale、ambiguous 或 unsupported：

Order.vue:   $t('order.save')
Toolbar.vue: $t('toolbar.save')

未迁移的旧调用：仍可走 MD5 compatibility fallback

默认 replace 是 preview；只有显式 --write 才写源码。写入时，源码、keyed catalogs 和 replacement metadata 作为一个事务提交，避免只替换部分文件。

检索练习

假设同一个 Vue template 中有两个没有 directive 的“保存”。第一轮 collection 后又插入一段源码，第二轮变成三个“保存”。请回答：为什么 MD5、当前坐标和 source text 都不足以安全决定旧 key？系统何时可以复用，何时必须暂停？

MD5 只认文案值；当前坐标会随插入而改变；source text 相同也无法区分三个 occurrence。系统应先用 semantic host、child role 和 local context 对照 collection history；只有候选唯一时才复用旧 key。若两个或更多历史 occurrence 都可能匹配当前片段，就为当前 occurrence 生成避开历史 key 的 proposed key，写 ambiguity report，并等待 i18n-key 或 identity-confirmations.json 的明确确认。这样不会把已有译文静默贴到错误位置。
