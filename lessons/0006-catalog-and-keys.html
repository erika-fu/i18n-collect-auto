从文本集合到可迁移的键控目录

本课用同一条“首页”对照 MD5、localization key、metadata fingerprint 和 location，解释它们为什么必须并存。

1. 四种输出，各自回答一个问题

产物主键回答的问题
zh_hash.jsonMD5(source text)运行时兼容字典里有哪些文本值？
zh_hash.map.jsonMD5(source text)这个文本出现在哪些源码位置？
catalog/zh.jsonlocalization key哪些稳定语义单元需要翻译？
catalog.meta.jsonlocalization key源文案、来源、指纹和位置是否发生变化？

“同一句出现两次”在 hash 字典里只需一个值，但在 metadata 里必须保留两个 location；同一业务 key 的源文案改变时，catalog 还要知道这是 changed，而不是无关的新文本。

2. buildCatalog 如何从 snapshot 构建目录

buildCatalog 遍历 snapshot → entry → location。每个 location 选择 key：

entry.key 存在且合法
  → 使用显式 i18n-key
否则
  → deriveKey({ path, kind, value })

派生 key 的形状是 pathSlug.sha256(projectPath + NUL + kind + NUL + value) 的前缀。它不加入 line/column，所以移动同一个文件里的同一语义文案不会因为位置变化而换 key；同文件、同 kind、同文本也会自然共享 key。

显式 key 和派生 key 的来源会在 metadata 中记成 explicit 或 derived，这对审计和冲突报错很重要。

3. 同 key 的多位置不是冲突

home.title → “首页” at App.vue:5
home.title → “首页” at Header.vue:9

这是同一个 source variant 的多个 locations，可以合并。真正的冲突是：

home.title → “首页” at App.vue:5
home.title → “主页” at Header.vue:9

buildCatalog 会按 key 建 group，再按 source text 建 variants。variants 多于一个时，conflictMessage 列出每个源文本、origin 和所有位置；Plugin 在写任何正式文件前失败。它不能擅自选择“第一个”，因为两个位置都是真实输入。

显式 key 恰好撞上另一条文案的派生 key，也属于同样的冲突。修复方式是给不同语义不同显式 key，或让同 key 的源文本一致。

4. fingerprint 不是 MD5

fingerprintOf 对源文本做 SHA-256，再取前 16 个 hex。它是 catalog metadata 中用于比较源文案版本的短指纹：

变化dictionarycatalog diff
只移动文字，文本不变可能位置变化unchanged
同 key 的“首页”→“主页”两个文本 hash 变化changed
新增 key新增文本 hashadded
key 从 A 改成 B，文本不变文本字节可不变A removed，B added

因此上一课说的“只改 i18n-key 会改 catalog、不必改 MD5 字典”是有条件的：源文本未变时，hash 字典确实可不变，但键控目录和 metadata 会变。

5. source catalog 是翻译输入，不是运行时 hash map

catalog/zh.json 是平面映射：

{
  "home.title": "首页",
  "order.submit": "提交"
}

翻译命令按这些 localization keys 请求 provider，替换命令也用 key 生成 t('home.title')。它不把 MD5 当业务键，因为 MD5 只表达文本内容，不表达“这是哪个稳定翻译单元”。

检索练习

两个文件都写了 i18n-key: home.title，一个文本是“首页”，另一个是“主页”。为什么这不是“同 key 的两个位置”，而是必须失败的 conflict？

同 key 多位置只有在 source text 相同才可合并；这里一个 key 有两个 variants。自动选择一个会让另一个位置丢失真实源文案，也无法安全决定目标译文，故在 writeOutputs 前放弃整轮。
