从“文本集合”到“可迁移的键控目录”

目标：理解为何保留 MD5 字典，同时新增 localization key、metadata 与冲突模型。

双轨输出解决兼容与迁移的冲突

产物key服务对象
zh_hash.jsonMD5(文本)既有 hash runtime consumer。
zh_hash.map.jsonMD5(文本)文本值到语义位置的兼容 source map。
catalog/zh.jsonlocalization key翻译与源码替换。
catalog.meta.jsonlocalization key来源、位置、指纹、变更比较。

MD5 适合“相同文本合并”；本地化键适合“一个翻译单元稳定演进”。将二者混为一谈会使旧运行时破坏或让翻译随文本修改失去追踪。

键如何产生

catalog.js 的 buildCatalog 遍历所有 snapshot entry/location：

  1. 若 entry 有来自指令的 key，它是显式键。
  2. 否则 deriveKey({ path, kind, value }) 生成 pathSlug.sha256-prefix。
// 输入：path + '\0' + semantic kind + '\0' + source text
// 不含 line/column
src.pages.Home.a1b2c3d4

省略坐标是有意的稳定性选择：同文件内移动同 kind 的同一文案不必使译文变成新条目。代价是同文件同 kind 同文本共享一个派生 key——这是合理去重。

冲突不是重复

同一 key 可对应多个位置，只要 source text 相同。若一个 key 对应不同 source text，就是无法安全自动决定译文语义的 key conflict。buildCatalog 聚成 variants，conflictMessage 列出每段文本、origin 与所有位置；Plugin 在写任何文件前失败。

一个显式 key 碰巧等于另一文本的派生 key 也冲突。修复原则很简单：不同源文本给不同 key，或使同 key 的文本相同。

fingerprint 与 diff 的职责

fingerprintOf 是源文本 SHA-256 前 16 hex。diffCatalog 比较旧/新 metadata：仅新为 added，仅旧为 removed，同键不同 fingerprint 为 changed，否则 unchanged。它比较的是源文本演化，不是运行时 MD5，也不是位置变化。

检索练习

把 i18n-key: home.title 从“首页”改成“主页”后，为什么 collect 必须失败而不是自动把目录改为“主页”？

如果它是同一位置从“首页”改成“主页”，它并不冲突，会正常成为 source-changed，保留目标翻译并标记 needs-review。只有同一轮中该 key 同时命名“首页”和“主页”两种 source text 时才失败；自动选择其一会悄悄丢失另一个位置的真实语义。

记忆锚点：hash 按文本回答“有哪些值”；catalog 按键回答“哪些语义单元需要翻译”；metadata 回答“这些单元从哪里来、是否变了”。
