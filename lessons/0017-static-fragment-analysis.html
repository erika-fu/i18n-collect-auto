从 AST 到 entry：Loader 如何精确识别中文片段

本课专门回答一个实现问题：源码里有普通字符串、模板字面量、字符串拼接、Vue 插值和 CSS content 时，Loader 究竟怎样区分它们？重点是“静态可证明片段”，而不是笼统地扫描中文字符。

1. 先建立总算法

输入：当前 resource 的原始 source

1. 根据 resource.block 选择语义解析器
2. 解析 source，得到带位置的结构
3. 遍历结构中的静态候选
4. 对每个候选：
   a. 得到 decoded value
   b. 判断是否含 Han 字符
   c. 判断是否是 import、排除指令或过滤上下文
   d. 确定 semantic kind
   e. 记录原始 start/end
5. 每个候选独立生成 entry
6. Loader 将 entries 包成 snapshot

entry = {
  value,
  locations: [{ path, kind, start, end }],
  key?                       // 可选的 i18n-key
}

核心原则是：先识别语法构造，再对构造内部的静态部分做 Han 判断。不能反过来先搜索所有中文，再猜它属于字符串、注释、属性还是 CSS selector。

2. 为什么使用 AST，而不是正则

JS/TS extractor 在 extract-script.js 中使用 Babel parser 和 Babel traverse：

const ast = parser.parse(source, {
  sourceType: 'unambiguous',
  plugins: ['jsx', 'typescript']
})

traverse(ast, {
  CallExpression(path) { /* localized call */ },
  StringLiteral(path) { /* 普通字符串 */ },
  TemplateLiteral(path) { /* 模板字面量 */ }
})

AST 解决了正则很难可靠处理的问题：

  • 知道引号里的内容是字符串，而不是注释或正则表达式的一部分；
  • 知道字符串的父节点是否是 ImportDeclaration / export module specifier；
  • 知道模板字面量的静态 quasi 和动态 expression 各在哪里；
  • 直接提供节点的 start/end，可以把 entry 定位回原始源码；
  • 能够区分嵌套表达式，例如模板中的 ${"内嵌"}。

HTML 与 CSS 也使用结构化解析：HTML 由 parse5 提供文本节点、属性节点和 source location；CSS 由 PostCSS 提供 declaration。这里的“AST”不一定都叫 Babel AST，但共同思想是先获得语义结构。

3. 普通字符串：StringLiteral 分支

const title = "首页"
const punctuation = "，。！"
const english = "Loading"
const modulePath = "./中文模块"
const message = "你" + unknown + "好"

遍历到 Babel 的 StringLiteral 后，当前实现按近似以下顺序处理：

  1. 如果节点是 import/export module specifier，跳过。
  2. 如果它是静态本地化调用的 key 参数，例如 t('home.title')，跳过普通字符串分支，由 localized-call 分支处理。
  3. 读取 node.value。这是 Babel 解码后的字符串值。
  4. 应用 exclusion directive 和 context filter。
  5. 执行 containsHan(value)；命中才创建 entry。
  6. kind 固定为 script-string，location 使用该节点的 start/end。
源码行为说明
"首页"收集一个完整值“首页”一个 StringLiteral
"，。！"不收集没有 Han
"./中文模块"不收集它是模块路径，不是用户文案
"你" + unknown + "好"收集“你”和“好”两个 entry两个独立 StringLiteral

4. 模板字符串：TemplateLiteral 的两条平行数组

JavaScript 模板字面量在 AST 中不是一个“最终字符串”。可以把它理解为两组互相交错的数据：

源码：`你好，${name}！`

node.quasis     = ["你好，", "！"]  // 静态片段
node.expressions = [name]           // 动态表达式

语义顺序：quasis[0] → expressions[0] → quasis[1]

提取器只遍历 node.quasis：

for (const quasi of nodePath.node.quasis) {
  const value = quasi.value.cooked
  if (!value || !containsHan(value)) continue
  entries.push(entry(
    value,
    location(source, resource.projectPath, quasi,
             'template-literal')
  ))
}

所以：

源码entry不会做什么
`你好${name}世界`“你好”和“世界”不读取 name 的运行时值
`a${x}中文${y}后缀`“中文”和“后缀”不把英文静态片段强行保留
`前${"内嵌"}后`“前”“内嵌”“后”不把三个值合并；内嵌字符串是另一个 AST 节点

外层 quasi 的 kind 是 template-literal；嵌套表达式里的普通字符串节点仍由 StringLiteral 分支处理，所以 kind 是 script-string。kind 来自节点/语义来源，不来自字符串长相。

5. “拼接”策略：项目选择不拼接

const a = "你" + unknown + "好"
const b = "你" + "好"
const c = `你${name}好`
const d = "你好，" + name

当前结果：

a → "你", "好"
b → "你", "好"
c → "你", "好"
d → "你好，"

这不是遗漏，而是有意的安全边界。若自动拼接，需要至少回答：

  • unknown 的运行时值是什么？
  • 条件表达式、函数调用、循环和异常路径会产生哪个结果？
  • 拼接后的一个翻译 key 应该定位到哪几个原始范围？
  • 翻译后的词序是否仍能适配原来的字符串加法？

项目因此采用保守规则：只收集“不执行程序也能证明的静态片段”。即使两边都是字面量，也不做常量折叠，因为一旦加入折叠规则，就会产生新的边界、位置和语义复杂度。动态拼接应通过显式本地化调用和参数化消息表达，而不是依靠自动收集猜测。

容易误解：“模板字面量被拆成片段”不等于“字符串拼接被支持”。模板字面量的静态 quasi 有明确 AST 边界；普通 + 表达式的最终值需要语义求值，当前项目不做这件事。

6. Vue HTML 中为什么仍然使用 Babel

<p>欢迎，{{ name }}！</p>
<input :title="'查看' + user.name">
<div>{{ `前缀${name}后缀` }}</div>

extract-html.js 先用 parse5 找到 HTML text node 或 allowlisted attribute，再把插值/动态属性内部的表达式交给 Babel。

parse5 HTML node ↓ 拆出普通文本和 {{ expression }} Babel parseExpression(expression) ↓ StringLiteral / TemplateLiteral / localized CallExpression ↓ push(value, kind, original source range)

表达式中的静态片段不会改成 script-string，因为它仍位于 HTML 语义位置：

  • Vue 插值中的字符串 → template-expression；
  • 动态 allowlisted attribute 中的字符串 → html-attribute；
  • 普通 HTML text node → html-text。

HTML entity 还需要额外保存“解码值”和“原始范围”的映射：例如源码 保存&#x540E;关闭 的 value 是“保存后关闭”，但 location 必须覆盖原始 entity 拼写。值不能反推范围，所以 extractor 在一次扫描中同时产出两者。

7. CSS 为什么不走 Babel，也不拼接 content

.badge::before {
  content: "第" counter(item) "项";
}

CSS extractor 使用 PostCSS 找到 content declaration，然后只扫描 declaration value 中的 CSS string：

"第"             → 一个 css-generated-content entry
counter(item)    → 忽略，运行时才知道值
"项"             → 一个 css-generated-content entry

CSS 中的多个字符串是多个静态 fragment，而不是一个可安全拼接的最终文案。这样每个 fragment 都有独立源码 range；counter、attr、var 等动态来源不被执行。

8. 从候选到 entry 的统一模板

function consider(value, kind, start, end, context) {
  if (!value) return
  if (!containsHan(value)) return
  if (context.isExcluded) return
  if (context.isFiltered) return

  entries.push({
    value,
    locations: [{
      path: projectPath,
      kind,
      start: offsetToPosition(source, start),
      end: offsetToPosition(source, end)
    }]
  })
}

各 extractor 的差别主要在“候选从哪里来”：

来源候选生成器范围来源
普通 JS 字符串Babel StringLiteralnode.start/end
JS 模板静态段Babel TemplateLiteral.quasisquasi.start/end
HTML 文本parse5 text nodenode.sourceCodeLocation + decode map
HTML 动态属性parse5 attribute + Babel expressionattribute 内容 + expression node
CSS generated contentPostCSS declaration + CSS string scannerstring start/end，排除引号

综合检索练习

请预测下面代码的 entry 值和 kind：

const x = `你好${user}世界`
const y = "你" + getWord() + "好"
const z = `前${"内嵌"}后`
import label from "中文路径"

结果是：你好（template-literal）、世界（template-literal）、你（script-string）、好（script-string）、前（template-literal）、内嵌（script-string）、后（template-literal）。中文路径位于 import module specifier，被排除。没有任何一步执行 user 或 getWord()，也没有把相邻片段拼接。

一句话记忆：AST 负责回答“这是什么语法构造”，Han 判断负责回答“这个静态值是否值得收集”，semantic kind 负责回答“它来自哪种语义位置”，source range 负责回答“原文在哪里”。四者共同生成一个 entry。
