配置与接入：让正确的模块真正经过 Loader

本课从 loadConfig 和 demo 的最终 Webpack 配置出发，解释“配置生效”究竟意味着什么，以及为什么 Loader 顺序是正确性条件。

1. 配置不是一个对象，而是一条合并管线

配置入口是项目根目录的 i18n-collect.config.js。config.js 的 loadConfig 不是简单读取它，而是按顺序构造最终配置：

DEFAULTS ↓ validate(file config) fileConfigHash = collectionHash(file config) ↓ merge(loaderOptions, 只允许 Loader 字段) ↓ merge(pluginOptions, 只允许 Plugin 字段) ↓ applyScopeOverrides（collect CLI 临时覆盖） 最终 config + configHash + fileConfigHash

先校验、再计算 fileConfigHash 很重要：它代表“文件本身声明的收集配置”，而不是某一次 CLI 临时覆盖后的结果。最终的 configHash 则代表本轮实际使用的收集规则。

2. 字段为什么有所有者

字段读取者改变它会影响什么
include/exclude、contextFiltersLoader / collect override哪些候选进入 snapshot
attributeAllowlist、styleExtensionsLoaderHTML 属性和样式资源的语义范围
outputPath/sourceMapFilenamePlugin正式 hash 产物和 source map 位置
catalogDir/sourceLocale/catalogFormatPlugin / translate源语言目录及其格式
translationProvider/targetLocales/translationFailuretranslate目标语言计划和失败策略

显式 Loader options 只能覆盖 Loader 字段，Plugin options 只能覆盖 Plugin 字段。于是一个“看似能传进去”的未知字段会直接报错，而不会被某一层悄悄忽略。

3. 两个 hash 不要混为一谈

假设只把目录从 lang/catalog 改成 i18n：

  • fileConfigHash 和 configHash 都不应因 catalog 位置变化而改变，因为 catalog 字段被排除在 collection hash 外；
  • 模块 metadata 仍可恢复：已有 snapshot 没有因为输出位置变化而变成“外来缓存”；
  • 新的 catalog 会写到新位置，但 hash source map 的语义配置不会无端变化。

反过来，如果修改 attributeAllowlist，它属于收集字段，hash 会变化；旧 metadata 的 fileConfigHash 与当前 root 不一致时不能使用。

4. include/exclude 的决策顺序

included = include 为空 || 某个 include 匹配
if (!included) return false
return !exclude.some(pattern => pattern 匹配)

因此 exclude 永远是最终否决。例如 include: ['src']、exclude: ['src/legacy'] 时，src/legacy/a.js 不收集。无通配符模式按路径边界匹配：src/foo 匹配自身和子路径，但不匹配 src/foobar.js。绝对路径、越出 root 的路径、空 root 模式都会失败。

5. 为什么 Loader 顺序决定“观察到什么”

Loader 链中普通函数从右向左执行；收集器必须在源码被转换前看到语义输入，并且必须位于 thread-loader 之前。worker 无法安全写主进程的 compilation/session，所以项目宁可明确失败。

Vue CLI 的最终规则要覆盖：

js rule
vue template：?vue&type=template
vue script：?vue&type=script
vue style：?vue&type=style
css rule
HTMLWebpackPlugin 的模板请求

HTMLWebpackPlugin 不是普通静态 HTML rule：它还要展开 EJS 标记并注入 bundle。demo 把请求构造成：

html-webpack-plugin/lib/loader.js?force=true
  ! i18n-collect/myloader
  ! public/index.html

读取顺序是 myloader 先观察并原样返回，HWP loader 再处理模板。没有 force=true 时，HWP 可能因检测到其他 Loader 而透传，导致模板标记不展开。

6. “接入成功”不是看配置文件，而是看证据

只添加 Plugin 不够，因为 Plugin 禁止扫描项目。每次 Loader 被调用，即使被 include/exclude 排除、没有 Han 文案或 style 不支持，也会留下 invocation metadata。Plugin 用它判断“规则已经接入，但本次为空”；完全没有 Loader 证据则报告 integration failure。

验证方法：用最终生成的 Webpack config 和 loader-order.test.js 检查，而不是根据 chainWebpack 注释猜执行顺序。

检索练习

配置里写了 include: ['src']，但最终 source map 没有任何条目。请按顺序列出四个可能边界：资源是否进入 Loader、include/exclude 是否通过、Loader 是否在主进程、extractor 是否找到 Han 文案。

先查最终 module request 是否真的匹配了 Loader；再查 include 通过且没有被 exclude 否决；再查是否被 thread-loader 移入 worker；最后才查 extractor 的语义范围和 Han 门槛。Plugin 不能靠扫描源码补上第一步缺失。
