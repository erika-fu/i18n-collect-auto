用测试证明边界，而不是只凭“看懂了”

最后一课把测试文件映射回系统边界，并给出一条可以安全修改项目的实践路径。

1. 测试按“契约边界”分层

层级代表测试它证明什么
资源分类与纯 extractorresource.test.js、*-extractor.test.js给定源码和 query，block、entry、kind、坐标、Han 门槛、指令是否正确
状态与目录session.test.js、catalog.test.js、occurrence-lifecycle.test.js、collection.test.js快照替换、独立 automatic key、history reuse、ambiguity confirmation、message contract、orphaned/retired 生命周期、key conflict、diff 和失败保留旧结果
Loader 契约loader.test.js、loader-order.test.jsthis、pitch/normal 透明传递、最终 rule 顺序和主进程限制
真实 Webpackwebpack-integration.test.js、watch-loop.test.jsVue/HWP query、cache、module graph 淘汰和 watch 收敛确实发生
CLI / 迁移cli-*.test.js、migration-workflow.test.js参数、退出码、网络授权、partial/strict、preview/write 和回滚

单元测试回答“纯函数给定输入如何输出”；集成测试回答“Webpack 是否真的按我们假设的链路调用它”。两者不能互相替代。

2. 先从一条真实文案画调用链

src/App.vue 的 template：“首页” ↓ Webpack 请求 ?vue&type=template myloader.pitch：读取原始 SFC ↓ describeResource resource.identity = src/App.vue::template[lang=html] ↓ extractHtml entry.value + html-text + 原始 start/end ↓ record module.buildInfo.i18nCollect + session.submit ↓ Plugin afterSeal 从当前 module graph 恢复合法 live snapshots ↓ buildCatalog 显式 i18n-key 或 automatic key + occurrence history + fingerprint ↓ release / writeOutputs zh_hash.json + zh_hash.map.json + catalog/zh.json + catalog.meta.json ↓ translate 缺失 target pair → provider draft → en.json + translation-state.json ↓ replace 重新验证 range / source text / adapter → preview 或 --write

每一条箭头都对应一个可以定位的测试边界。出现错误时，先问“错误发生在哪条箭头”，不要从 CLI 末端盲猜。

3. 先写失败测试，再做最小改动

  1. 明确新行为属于资源分类、extractor、配置、session、catalog、adapter 还是 CLI。
  2. 在最小 fixture 中写一个会失败的测试，固定输入、期望 entry 和 location。
  3. 只修改该边界的实现；不要用 Plugin 扫描或全局 special case 补洞。
  4. 先跑对应单元测试，再跑 Loader/真实 Webpack 集成测试。
  5. 最后跑完整 npm test，确认兼容产物、watch 和失败回滚没有回归。

例如要新增一种 HTML 属性收集：第一站是 extract-html 和 attribute allowlist；然后补坐标、指令、Han 门槛、loader integration；不能只修改 catalog 让它“看起来出现”。

4. 用测试读懂缓存和事务

测试一个缓存命中场景时，必须验证三件事：

  • Loader 没有重新执行，但 module metadata 仍能恢复 snapshot；
  • metadata 的 root/config hash 不匹配时不会使用外来 snapshot；
  • 当前 module graph 移除资源后，旧 snapshot 不再进入 live set。

测试一个输出失败场景时，必须检查四类文件都保持上一成功字节，而不只是检查函数抛错。测试 watch 时还要检查“真实变更最多产生一次 follow-up compilation；相同字节不再写入”。

5. 用测试读懂替换的保守边界

替换测试不应只断言生成了 t('key')，还要覆盖：

场景期望
range 文本已变化skip mismatch，绝不写
已有 $t()already localized，不嵌套
不支持的 AST 位置带理由 skip
多个 edit 重叠拒绝规划
strict 有一个 skip整个 write 零变化
write 中途失败source/catalog/metadata 一起恢复

6. 掌握验收：从回忆到修改

不要把“读过十课”当作掌握。请在不看讲义时完成：

  1. 解释 src/App.vue::template[lang=html] 为什么是内部 resource identity，而 map 使用 locations。
  2. 说出 Loader Context 中 resourceQuery、this.data、_module 各自解决什么问题。
  3. 给一个 Vue template、script string 和 CSS content，预测它们分别进入哪个 extractor。
  4. 解释 candidate、live snapshot、committed output 的区别，并说明失败时谁保留。
  5. 给一个显式 key 冲突、一个 occurrence identity ambiguity 和一个源 fingerprint 变化，分别预测 collection 与 translate 的行为。
  6. 对一个 stale source range 做 replace preview，解释为什么 strict/write 都不能绕过 mismatch。
  7. 针对一个小改动先写失败测试，再实现，再运行完整测试。

终检索题

请分别用一句话回答：为什么 collection 必须由 Loader 拥有？为什么 catalog metadata 必须保存 fingerprint/location？为什么 translation 要有 review state？为什么 replacement 默认 preview？

Loader-owned collection 保留真实 module/语义边界并避免项目扫描；metadata 用 fingerprint 识别源文案演化、用 location 验证和追溯；review state 防止源文案变化时静默覆盖既有译文；preview-first 让潜在破坏性的源码编辑先可见、可审阅、可拒绝。
