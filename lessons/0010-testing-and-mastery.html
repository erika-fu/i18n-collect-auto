用测试证明边界，而非凭眼熟判断

先将故障映射到其契约边界，再运行最小的相关测试，最后才依赖完整迁移工作流。

1. 测试按契约边界组织

层次代表性测试证明的内容
分类与提取器resource.test.js、*-extractor.test.js资源身份、条目、指令、本地化调用识别、kind、范围与过滤。
Catalog 状态catalog.test.js、catalog-lifecycle-source-localized.test.jsULID key、v1/v2→v3 迁移、身份恢复、歧义、契约、调用、孤立、退役与冲突。
Loader/Pluginloader.test.js、webpack-integration.test.js、watch-loop.test.js透明 loader 行为、基于图的快照恢复、缓存、事务与 watch 收敛。
CLI 集成collection-catalog-integration.test.js、end-to-end-migration-workflow.test.jscollect 到 catalog 的身份连续性、失败轮次保留、翻译、替换与运行时迁移。

单元测试说明边界对固定输入做什么；真实 Webpack 与端到端测试证明系统能通过公共工作流实际抵达该边界。

2. 追踪一条当前生命周期

源文本“请稍候” ↓ loader/extractor 提交 source-text occurrence ↓ catalog 构建 metadata v3 ↓ 分配或唯一恢复 auto.<ULID> ↓ translate 根据 fingerprint 接受目标文本 ↓ replace --write 将源码改为 t('auto.…') ↓ 后续收集识别 localized-call ↓ 同一 key 保持 active；规范源文本/fingerprint 保留 ↓ 后续源文本变化 → 目标翻译 needs-review

核心设计断言是：替换不应抹除翻译上下文。本地化调用提供位置和结构锚点，而 metadata 保留规范源文本。

3. 安全地新增行为

  1. 命名边界：提取器、指令、catalog 生命周期、plugin/session、适配器或 CLI。
  2. 编写聚焦的失败 fixture，固定源码、预期 metadata 与预期失败/保留行为。
  3. 只修改拥有该职责的模块；不要添加 Plugin 扫描或全局特例。
  4. 运行聚焦测试，再运行受此次改动影响的集成层测试。
  5. 在宣称迁移安全前运行完整测试套件。

若新增一种 localized-call 形态，应从 localized-call.test.js 和提取器测试开始，再到 catalog 生命周期测试——而不是替换测试——因为收集拥有识别和生命周期校验的职责。

4. 防止身份被静默损坏的断言

场景必要断言
Metadata 升级v1/v2 到达 v3 时不重写既有本地化 key。
历史歧义正式输出与最近一次成功结果逐字节一致；报告稳定的建议 key。
未知调用除非 key 是 external 或旧 MD5 字典 key，否则本轮失败。
源文本 + localized-call一个 key 保持 active；规范源文本不能被空调用值替换。
孤立项 + 调用调用将未退役的孤立项恢复为 active。
退役只有确认/策略才能移除 metadata；稍后由 translate 清理目标项。

5. 掌握检查：先预测再阅读

  1. 解释为何自动 key 不透明却仍稳定。
  2. 区分 catalog.meta.json 与 replacements.json。
  3. 预测 t('unknown.key')、外部 key 与 MD5 调用的收集行为。
  4. 解释为何所有活动 occurrence 都是本地化调用时仍必须保留源文本。
  5. 说明两种持久化确认歧义的路径。
  6. 指出 key 冲突、歧义或未知调用后哪个输出保持不变。

最终检索问题

带有 key auto.X 的 source-text occurrence 被替换成 t('auto.X')。下一次收集时，metadata 必须保留什么？为何将调用视为一个空的源文本值是错误的？

Metadata 必须保持 auto.X 为 active，更新调用 occurrence 的位置/锚点和 representation，并保留规范源文本与 fingerprint。空调用值不是源消息；用它覆写规范源文本会破坏翻译审阅信息，使 catalog 丢失有意义的源文本。
