NEW SERIES · 07 / 07 · VUE LOADER LIFECYCLES

为什么 vue-loader 可以“先于”子请求的 myloader.pitch？

本课区分 Vue SFC 的根模块请求与 script、template、style block 子请求，避免把跨请求的递归构建顺序误认为同一条 Loader 链中的 pitch/normal 执行顺序。

1. 先区分两个层级

对普通 JavaScript，Webpack 可以直接处理一个请求：

src/main.js
  ↓
匹配 JS Loader 链
  ↓
myloader、thread-loader、babel-loader

但一个 Vue 单文件组件有额外一层。以 src/App.vue 为例：

根请求：src/App.vue
  ↓
vue-loader 解析 SFC 结构
  ↓
生成组件模块，并依赖 block 子请求
  ├─ src/App.vue?vue&type=script
  ├─ src/App.vue?vue&type=template
  └─ src/App.vue?vue&type=style&index=0&lang=css

子请求不是磁盘上的新文件，而是同一个 App.vue 的不同语义资源。Webpack 会把每个子请求当成独立模块：重新匹配规则、创建独立 Loader Context，并运行独立的 Loader 生命周期。

2. 同一个请求中的顺序从不例外

假设 Webpack 为一个具体 request得到以下最终 Loader 列表：

配置列表：A → B → C

执行顺序固定为：

pitch：   A.pitch() → B.pitch() → C.pitch()
normal：  C()       → B()       → A()

因此，同一个 request 不会发生这种交错：

错误理解：A.pitch() → C() → B.pitch()

除非某个 pitch 返回结果而短路请求，否则 Webpack 会先完成该 request 的 pitch 遍历，再开始 normal 遍历。

3. 为什么 Vue 的顺序看起来不同？

“vue-loader 先运行，子请求的 myloader.pitch 后运行”比较的是两个 request：

Request A：App.vue
  └─ 根模块的 vue-loader 生命周期
       ↓ 创建 / 发现依赖

Request B：App.vue?vue&type=template
  └─ template 子模块自己的 Loader 生命周期
       └─ myloader.pitch()

这不表示 vue-loader 的 normal 函数插到了 Request B 的 myloader.pitch() 前面。它只表示根 SFC 模块先暴露出后续要构建的 block 模块，Webpack 再递归构建这些模块。

4. 本项目如何把 myloader 接到 Vue block？

Vue demo 不是把 collector 简单放到根 App.vue 的 vue-loader 前或后，而是用 resourceQuery 选择 block 子请求：

type=template → 加入 myloader
type=script   → 加入 myloader
type=style    → 加入 myloader

当 collector 处理 template 请求时，Loader Context 的关键字段可理解为：

resourcePath:  /project/src/App.vue
resourceQuery: ?vue&type=template&id=abc

resourcePath 指向完整物理文件；resourceQuery 标明当前语义 block。describeResource 会将它规范化为：

projectPath: src/App.vue
block: template
identity: src/App.vue::template[lang=html]

style 请求还必须包含 index，以区分同一个 SFC 中多个独立的 <style> block；这与 CSS cascade 无关。

5. myloader 到底什么时候收集？

myloader 的正常路径在 pitch 中主动从磁盘读取原始文件：

loader.pitch = function pitch() {
  runCollect(this, fs.readFileSync(this.resourcePath, 'utf8'))
  this.data.collected = true
}

pitch 没有 Webpack 自动传入的 source 参数。这里的原始源码来自 fs.readFileSync(resourcePath)，而不是来自 vue-loader 或模板编译器的输出。

对 Vue 子请求，collector 再用 query 选出原始 SFC 中正确的 block：

App.vue 原始文本 + type=template
  ↓
定位原始 <template> block
  ↓
extractHtml
  ↓
src/App.vue 的准确行列位置

6. normal 阶段的后备路径防御什么？

正常情况下，pitch 已完成收集，normal 函数只原样传递：

if (!this.data || !this.data.collected) runCollect(this, source)
this.callback(null, source, sourceMap, meta)

只有 pitch 没有完成收集时，才会用 normal 阶段的 source 作为后备。对于 Vue block，这个 source 可能已经被同一子请求中、位于 collector 右侧且在 normal 阶段先运行的 Loader 改写，例如 template compiler、Babel 或 CSS transform。

所以 Vue 分支会重新读取完整原始 App.vue，而不是信任 fallback source。这不是因为 myloader.pitch 收到了被 vue-loader 改写的源码；相反，pitch 本来就主动读取原始磁盘字节。它是为了保证后备收集仍以原始 SFC 和原始坐标为准。

7. enforce 改变什么？

Webpack 的 enforce: 'pre'、普通规则和 enforce: 'post' 会影响最终 Loader 列表如何组成。可以先将它理解为：

pre rules → normal rules → post rules

但 enforce 不会创造新的执行阶段。最终列表确定后，每个 request 仍遵守同一规则：

pitch：从左到右
normal：从右到左

inline Loader request 的前缀也可能决定哪些 normal、pre 或 post 规则参与。因此不能只根据 chain-webpack 声明的先后、rule 名称或注释判断运行顺序；必须检查最终 Webpack config，最好用真实编译测试验证。

检索练习

有人说：“既然 vue-loader 已经 normal 执行过，App.vue?vue&type=template 中的 myloader.pitch 一定拿到 transformed source。”这句话哪里不准确？请分别说明根 request、block request 与 myloader.pitch 的原始输入来源。

根 App.vue request 与 template block request 是独立模块和独立 Loader 生命周期。vue-loader 在根 request 中解析 SFC 并暴露 block 子请求；随后 Webpack 构建 template request。myloader 的 pitch 没有接收 source 参数，而是用 fs.readFileSync(resourcePath) 主动读取原始 App.vue。只有 pitch 未收集、进入 normal fallback 时，传入的 source 才可能已被当前 block 链中的后续 Loader 转换。

本课结论：先问“这是同一个 request 吗？”，再问“这是 pitch 还是 normal 吗？”。根 SFC 与 block 子请求的递归关系，不能替代同一 Loader 链的执行顺序。
