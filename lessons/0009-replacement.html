源码替换：先验证，再生成，再决定是否写入

本课逐步解释为什么 replacement 不重新收集、如何从 metadata 定位原文、adapter 如何选择调用，以及 preview/strict/write 的差异。

1. replacement 的事实来源是什么

replace.js 读取 catalog metadata 中的 localization key、source、occurrence location，而不是再次扫描整个项目寻找中文。两个相同的文案 occurrence 可能拥有不同 key，因此 replacement 绝不能按文本值或 MD5 统一替换：

catalog.meta.json
  src.pages.Order.8f31a2c4 → source: "保存"
    occurrence location: src/Order.vue:5:4..5:6 (html-text)
                ↓
replace 读取当前 src/Order.vue
  → 按 line/column 计算 offset
  → 检查当前 slice 是否仍等于“首页”
  → 再决定 edit / skip / already localized

如果源码在 collect 之后被手工改动，range 仍在但文本不匹配，就 skip catalog location does not match the current source，而不是盲目替换新内容。这样 collection 和 replacement 的事实边界分开：collection 发现，replacement 验证并编辑已发现的位置。

2. 为什么 replacement 可以读源码，而 Plugin 不能

收集阶段的 Plugin 如果扫描源码，就会绕过 module graph 和 Loader 语义；替换阶段本来就必须验证 runtime 能力、当前文本和 AST 位置，因此 CLI 可以对项目文件做受限 discovery。两者任务不同：

阶段读取源码的目的能否创造新的收集条目
Loader/extractor在真实模块语义中发现文案能
Plugin聚合 metadata / graph不能，禁止扫描
replace验证已有位置和运行时适配器不能，只能处理 metadata 中的项

3. adapter 先确定“调用谁”

adapter生成形式先决条件
jst('home.title')项目中已有导出名为 t 的本地化函数；不会插入 import
vue2template 用 $t；Options method 用 this.$tvue-i18n 8 且已有 VueI18n 使用/实例
vue3template 用 $t；script setup 用已有 t；Options 用 this.$tvue-i18n ≥9 且已有 createI18n

运行时检测只证明“可调用的既有设施存在”，不会替用户安装依赖、改 bootstrap 或创造变量。没有这些条件时，replace 在规划阶段失败或 skip，避免生成一段无法运行的代码。

4. 一个 script 片段如何成为 edit

planner 会先解析 AST，拿到 metadata 的 range 对应的 literal，再按语义位置判断：

  • 变量初始化、赋值、return、throw、调用参数、数组元素、对象 value、条件/逻辑/二元/序列表达式等可编辑位置，才继续；
  • 对象 key、switch case、无法确认作用域的箭头函数等位置 skip；
  • 已经位于 t()、$t() 或 this.$t() 中则记为 already localized，不嵌套调用；
  • 多个 edit 发生重叠时拒绝，避免一次写入破坏另一条替换。
const title = '首页'
       ↓ vue3 / js adapter
const title = t('home.title')

Vue template 文本会生成 {{ $t('home.title') }}；静态属性可能需要从 title="首页" 改成绑定形式 :title="$t('home.title')"。HTML entity 解码后的值仍要与原始 slice 对齐。

5. skip 是安全设计，不是失败吞掉

以下情况会在 preview 中显式给出理由：

source range 不再匹配
Vue template / attribute 不属于所选 adapter
React JSX 超出当前替换范围
CSS generated content 或独立 HTML 不在 replacement scope
对象 key / switch case 不是支持的语义位置
已有 t/$t/this.$t

“collect 能识别”只代表能静态记录；“replace 能编辑”还要求知道运行时调用、语法位置、作用域和生成代码。宁可报告 skip，也不生成表面上合理但运行时错误的代码。

6. preview、strict、write 三个开关

模式行为源码是否写入
默认 preview输出每文件新 content、replacements、skipped、already localized否
--strict只要有 skipped，整个 replace 不提交否；退出 7
--write准备 source、catalog artifacts、replacements.json 的完整目标集是；通过 journal 原子提交

--strict --write 是“全部候选都能安全处理才写”的门。非 strict write 可以提交已规划的 replacements，但 skipped 会保留在报告里供审阅。

7. 写入为什么仍然是事务

替换不只改源码，还可能更新 catalog 和 replacement metadata。commitFiles 对整组目标使用同一 journal：任何文件写入失败都恢复 source、catalog 和 metadata，不能留下“源码已替换但目录没更新”的半迁移状态。

重复运行时，已生成的 t()/$t() 会被识别为 already localized；不再套一层调用，因此 replacement 具有幂等性。

检索练习

metadata 记录的 key 是 src.pages.Order.8f31a2c4、文本是“首页”，但开发者在 replace 前把源码改成“主页”。默认 preview、--strict 和 --write 分别应该发生什么？

三者都会先发现当前 slice 与 metadata source 不匹配并产生 skip；默认 preview 输出 skip 但不写；strict 因 skip 退出 7 且零写入；write 也不能绕过验证，因此不会把“主页”误替换成 home.title。
