先建立四层地图：构建、快照、目录、替换

本课的目标不是记住名词，而是能沿着一条文案，解释它从 Webpack 模块进入收集器后，为什么会出现在某个输出文件里。

1. 项目到底在做什么

它不是“扫描整个项目目录，找出所有中文”的脚本。只有进入 myloader 的资源才会被收集；Loader 观察资源并提交快照，Plugin 在一次 compilation 成功后汇总并发布结果。

Webpack module request ↓ myloader：识别语义资源，提取候选文案，提交 resource snapshot ↓ MyI18nPlugin：收集本轮所有仍存活的 snapshot，验证并聚合 ↓ zh_hash.json + zh_hash.map.json + source-locale catalog ↓（可选） translate：根据 catalog 生成目标语言目录 ↓（可选） replace：预览或显式写入源码改写

四个阶段故意分开：收集不依赖翻译服务，翻译不修改应用源码，替换默认只预览。这种分离让每个阶段都能单独失败、重试和验证。

2. 三个“键”不是同一个东西

概念例子它回答的问题
资源身份src/App.vue::template[lang=html]哪一个语义资源的快照需要被替换？
文本 hashmd5('首页')相同文本如何兼容旧的运行时字典并去重？
本地化键home.title翻译目录和源码替换使用哪个稳定的业务名称？

资源身份：文件路径后面为什么有两个冒号

src/App.vue::template[lang=html] 可拆成：

  • src/App.vue：项目相对路径；
  • ::：路径和语义 block 的分隔符；
  • template[lang=html]：该 Vue 文件的 template block，语言按默认值规范化为 HTML。

同一个物理文件会产生多个独立身份：

src/App.vue::script[lang=js]
src/App.vue::template[lang=html]
src/App.vue::style[index=0;lang=css]

这样删除 template 中的文案时，不会把 script 或 style 的贡献一起覆盖。资源身份是收集器内部的快照管理键，不是最终 source map 的字段。

3. 为什么 zh_hash.map.json 没有 resource

这是一个容易混淆的边界。内部 snapshot 可能长这样：

{
  "identity": "src/App.vue::template[lang=html]",
  "projectPath": "src/App.vue",
  "owner": { "block": "template", "lang": "html" },
  "entries": [ ... ]
}

但对外的兼容 source map 仍然是 version 1 结构：

{
  "version": 1,
  "parserVersion": "babel-7",
  "configHash": "...",
  "entries": [
    {
      "key": "<md5>",
      "value": "首页",
      "locations": [
        {
          "path": "src/App.vue",
          "kind": "html-text",
          "start": { "line": 5, "column": 4 },
          "end": { "line": 5, "column": 6 }
        }
      ]
    }
  ]
}

因此要记住：identity 用来管理“哪份快照替换哪份旧快照”；path/kind/start/end 用来让人追溯“这句文案在原文件什么位置”。项目明确不把 resource identity 写进哈希词典或 source map。

4. “快照替换”与“增量构建”并不矛盾

Webpack 的增量性和收集快照的更新策略是两个维度：

维度问题本项目的答案
构建执行这次需要重新处理哪些模块？由 Webpack module graph、依赖失效和缓存决定。
资源状态某个已处理资源当前贡献哪些文案？以该资源的完整新 snapshot 替换旧 snapshot。
项目结果本轮哪些资源应该进入产物？聚合当前 module graph 中仍存活且已验证的 snapshots。

例如：

旧 snapshot：App.vue::template → 首页、欢迎回来、提交
当前源码：  App.vue::template → 首页、提交
新 snapshot：App.vue::template → 首页、提交

如果只追加“新发现的文本”，收集器没有可靠的删除语义，“欢迎回来”会永久残留。差量方案可以计算 added 和 removed，但仍必须拿到旧完整状态并重新得到当前完整状态；直接提交当前快照更容易处理重试、缓存、事件顺序和失败回滚。

这不是“每次重扫整个项目”：Webpack 仍可以只重建受影响的模块，未重跑但仍存活的模块可从 metadata 恢复快照。替换发生在一个资源身份的状态上，不是整个项目文件无条件重写。

5. 文件维度还是模块维度？

日常可以说“改文件触发重建”，但 Webpack 的调度和缓存核心是 module graph。普通 src/message.js 往往近似一个物理文件对应一个模块；Vue SFC 则会把一个物理文件拆成多个带 query 的模块请求：

src/App.vue?vue&type=script&lang=js
src/App.vue?vue&type=template&lang=html
src/App.vue?vue&type=style&index=0&lang=css

因此可以近似地说“修改 template 会让整个 .vue 相关构建流程重新评估”，但不能说它一定只重跑一个文件或一定只重跑 template。具体哪些模块失效，取决于 vue-loader、依赖关系和缓存命中。

精确表述：失效源头是物理文件变化；Webpack 处理的是关联的模块请求；i18n-collect 再把这些请求规范化为独立的语义 resource identity。

检索练习：不看答案先说完整链路

修改 src/App.vue 的 template，删除“欢迎回来”，但没有改 script。请回答：

  1. 为什么旧文案不会因为“只追加”而永久保留？
  2. Webpack 的模块处理和 resource snapshot 的替换分别发生在哪个层面？
  3. 最终 zh_hash.map.json 会使用哪个字段定位源码，而不是使用 resource identity？

重新处理后，src/App.vue::template[lang=html] 提交只包含当前 template 的完整快照，因此“欢迎回来”从该资源的贡献中消失；Webpack 是否重跑 script 等关联模块由 module graph/cache 决定。最终 source map 使用 locations[].path、kind 和行列坐标定位原始源码，不写入 resource。

本课结论：项目的最小理解单元不是孤立字符串，而是“一个语义资源在一次 collection round 中提交的、可替换且可验证的 snapshot”。
