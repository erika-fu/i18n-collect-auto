替换后，调用仍是收集证据

把源文本替换为运行时调用，不能让 catalog 忘记已翻译的内容。本课介绍静态调用如何参与收集、校验和 key 生命周期。

1. 支持的静态调用形态

localized-call.js 仅识别以下调用中的静态第一个参数：

t('home.title')
$t('home.title')
this.$t('home.title')
t('items.deleted', { count })

计算成员、可选调用、动态 key 和其他形态不会被误分类。script 与 HTML 提取器会产生一个 localized-call occurrence，其 value 为空，因为调用本身提供的是 key，而不是新的中文源文本。第二参数若是静态对象字面量，会记录参数名；需要占位符却传入动态对象时，收集 fail-closed。

1.1 显式消息清单 vs 自动完整静态文案

在未声明运行时多语言边界的区域，完整静态中文可以留在源码里，由收集分配 automatic key。插值、拼接、条件构造与格式化不是完整静态文案：不要把片段当作可独立翻译单元。带变量、复数或需要运行时多语言渲染的消息，应在 explicit-messages.json 声明规范中文源文案与派生 placeholder 契约，再以静态 localized-call 引用该键。清单只读；成功收集后规范文案进入源语言目录与 metadata，源文编辑保留键、更新 fingerprint，并把目标译文标为 needs-review。

用 i18n-collect check-policy 做本地校验：每条违规带策略原因与源码位置。既有完整静态文案违规可写入 complete-static-copy-baseline.json 做增量迁移；baseline 只 grandfather 精确匹配，新增或改动违规会失败，且不能掩盖收集失败、身份歧义、过期正式产物，或运行时多语言边界内的直接源文案。

1.2 结构化消息与有意共享翻译

把一句用户文案拆成「请阅读我们的」+ 链接文案 + 「与」+ 另一段链接文案，再各自 automatic 翻译，会在目标语言里打乱语序，也可能把控件或链接从赋予其含义的句子里拆开，损害可访问性。此类含链接、强调、控件或组件插槽的结构化消息必须走显式本地化：在清单里写整句，例如 请阅读我们的{terms}与{privacy}，由译者重排占位符，运行时用静态调用或组件插值填槽。需要多处共用同一译文时，有意共用同一显式键且 message contract 一致；普通相同静态中文默认仍各自独立 automatic key。

check-policy 对这类交错拆片报告 structured-fragmentation，并提示改用显式本地化，而不是把片段写进 baseline 继续自动收集。

1.3 运行时多语言边界 ≠ 已被收集

需要在运行时切换目标语言的功能或路由，应写入 runtime-multilingual-boundaries.json：每个边界有 id、include 与可选 exclude，pattern 语义与收集的 scope pattern 相同。路径命中某边界 include 且未被该边界 exclude 否决即属边界内；重叠边界取并集，因此一个边界的排除区可被另一边界重新纳入。

边界内不允许直接面向用户的中文源文案（含 no-i18n-auto），只允许静态 t() / $t() / this.$t()。违规原因为 runtime-multilingual-literal，且不能被完整静态文案 baseline grandfather。被收集进目录只说明有 automatic 或显式身份，并不等于运行时能切语言；边界外仍可中文优先自动收集，边界内必须显式本地化。

2. 调用不会替代规范源文本

替换前 home.title → 源文本“首页” + source-text occurrence 替换后 $t('home.title') → localized-call occurrence home.title → 仍保留规范源文本“首页” + 相同 fingerprint

当 source-text 和 localized-call occurrence 并存时，二者都是同一个活动 key 的位置。若只剩调用，收集会恢复此前 catalog 条目的规范源文本和 fingerprint。这保留了翻译上下文，并让之后的源文本修改正确地将翻译标为 needs-review。

3. 引用校验保护 catalog

调用目标收集结果
活动项目 key保持活动状态并添加调用位置。
未退役的孤立 key恢复为 active。
显式消息清单中的 key用声明源文案播种目录条目，并校验参数契约。
未知项目 key本轮失败；保留此前正式输出。
已退役 key本轮失败。
占位符不匹配 / 动态参数本轮失败；不发布部分正式输出。
配置的 externalKeys 成员允许调用，但不创建项目条目。
32 位旧 MD5 key为兼容性而置于带 key 的项目 catalog 之外。

externalKeys 是 Plugin 拥有的配置字段，因为它改变的是 catalog 生命周期策略，不是提取语法。

4. 共置指令不能互相矛盾

紧邻调用的指令可以重复其 key，但不能为调用改名：

// i18n-key: home.title
$t('home.title')  // 有效

// i18n-key: other.title
$t('home.title')  // 收集失败

提取器通过共享的指令规则尽早检测此情况。若允许不一致，同一源码位置便会声称拥有两个运行时身份。

5. 孤立与退役是刻意划分的阶段

删除当前 occurrence 不会立即删除身份。metadata 条目会变为 orphaned，源语言消息不再包含它，但目标翻译仍保留。之后的调用可以将它恢复。只有通过 retirement-confirmations.json 或 pruneOrphaned: true 才会退役；随后下一次 translate 会移除目标 catalog/状态数据。

重要：同一轮中对正在退役的 key 发起调用会被拒绝。收集绝不会将一个 key 同时视为有意退役和正在使用。

6. Representation 字段说明来源

Metadata v3 在条目和 occurrence 记录上都写入 source-text 或 localized-call。这并不替代 script-string 等语义 kind：语义 kind 标识源码位置，representation 则表明此位置是提供规范源文本，还是引用已有 key。

7. 调试顺序

  1. 确认调用是受支持的静态形态，且参数是非空字符串。
  2. 在 catalog.meta.json 中确认 key 是 active 还是 orphaned。
  3. 对于未知的外部集成，请将 key 加入 externalKeys，不要杜撰 source-text 条目。
  4. 对于已退役 key，请恢复有效的 catalog 身份，或删除/修改调用；不要绕过校验。
  5. 更改输出前先检查失败原因：失败轮次会有意保留最近一次成功输出。

检索练习

执行 replace --write 后，banner.title 的最后一个 source-text 位置变为 $t('banner.title')。收集会记录什么，又会从此前 metadata 保留什么？

它会在调用参数位置记录一个 localized-call occurrence，保持 banner.title 为 active，并保留此前的规范源文本与 fingerprint。调用维持结构/位置证据；保留的源文本则维持翻译单元及审阅基线。
