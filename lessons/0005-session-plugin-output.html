一次收集轮次如何安全地成为正式结果

目标：掌握候选/已提交状态、缓存恢复、冲突阻断与多文件事务。

Session 是 compiler 边界内的状态机

session.js 用 WeakMap<root compiler, CollectionSession> 隔离多个 compiler、并行构建与测试实例，也允许结束的 compiler 被回收。每个 main compilation 有候选 round：

begin → submit / noteInvocation / warn ↓ afterSeal：读取当前 graph metadata、诊断接入 ↓ (done, build 成功) assemble live snapshots → catalog conflict check ↓ release = checkpoint → 内存 commit → disk write ↓ ↓ throws └────────────── success rollback + abandon

为什么 metadata 是关键而不是缓存漏洞

Loader 将普通可序列化信封写进 module.buildInfo.i18nCollect：schema version、canonical root、fileConfigHash、是否 included 和 snapshot。Plugin 可从当前 main/child module graph 恢复它，因此未变模块或 filesystem cache 命中时，快照不会消失。

interpretMetadata 同时检查 schema、root 和 file config hash。任何外来/过期/损坏 metadata 会诊断并使轮次失败，绝不发布“可能属于另一构建”的文本。

Plugin 做什么，明确不做什么

MyI18nPlugin 在 thisCompilation 建立 round，在 afterSeal 检查 loader 证据，在 done 汇总并发布。它可读取 module graph、session metadata、配置和输出路径；它不可读取/解析业务源文件或调用 extractor。

静态 HTML 是特殊生命周期：HWP child compilation 缓存命中时 Loader 本轮可能不执行。retainStaticHtmlSnapshots 只在模板仍配置、是 file dependency、存在且在 scope 时保留已提交快照；失去任一条件则淘汰。

正式输出是一个原子集合

成功 collection 同时发布：MD5 runtime dictionary、v1 source map、源 locale catalog、catalog metadata。output.js 先比较字节，完全相同则不写；否则 journal 记录 temp/backup/final，写临时文件、备份旧文件、替换新文件，最后删 journal。中断或失败时恢复；下一次提交先恢复残留 journal。

这同时满足两个外部可见保证：失败绝不发布部分结果；watch 不会被相同内容的无效写入无限唤醒。

一个真实限制，不应掩盖

应用 bundle 在构建开头导入 dictionary，Plugin 在构建末尾才知道完整新 dictionary。因此一次生产构建会在磁盘写出最新产物，但同次 bundle 可能仍嵌入旧字典。watch 会因真实改动多编译一次，下一轮相同字节不再写，最终收敛。项目有意未引入双阶段构建。

检索练习

catalog key conflict 为什么由 Plugin（而不是单个 Loader）在输出前检查？

冲突的定义跨资源：同一 key 能在多个 Loader 调用中出现，只有聚合所有 live snapshots 才能知道它是否命名不同源文本。Plugin 在 buildCatalog 后、writeOutputs 前失败，故整个正式集合保持上一成功版本。
