从 Module metadata 到正式输出：一次收集轮次如何安全完成

本课把 Webpack 的 Compiler、Compilation、Module 与缓存，和 i18n-collect 的 Session、round、metadata、live set、candidate、committed 串起来，说明 Plugin 如何在不重新解析所有源码的情况下形成完整且可回滚的收集结果。

1. 先区分 Webpack 的构建对象

一次普通构建通常有一个 root Compiler、一个主 Compilation 和多个 Module。watch 模式复用同一个 Compiler，但每次重新构建都会产生新的 Compilation。

一个 Node.js 进程
└── root Compiler
    ├── Compilation 1
    │   ├── Module A
    │   ├── Module B
    │   └── Module C
    ├── Compilation 2（文件变化后）
    └── Compilation 3

当前 Compilation
├── modules：本轮模块节点集合
├── moduleGraph：模块之间的依赖关系
└── chunkGraph：Module 到 Chunk 的映射

Module 的边界由模块请求经工厂解析后的身份决定，通常受 resource、loader chain、query 和 module type 共同影响，并不是简单的“一个文件”或“一个 Loader”对应一个 Module。Vue SFC 可能被拆成多个请求，例如 script、template 和每一个 style block。

一个 child compilation 也是 Compilation，但它属于某个主构建。项目通过 mainCompilation() 沿 parentCompilation 找到主 Compilation，使同一主构建的 child compilation 归入同一个 round。

2. Session 与 round 的边界

session.js 用模块级 WeakMap 保存：

root Compiler → CollectionSession

这个映射只存在于当前 Node.js 进程。它不是跨命令的持久化存储；进程退出后，Session、round 和内存中的 committed 都消失。watch 模式中同一个 Compiler 持续存在，因此会复用同一个 Session；不同 Compiler 在同一进程中则使用不同 Session。

每个 CollectionSession 内部再用另一个 WeakMap 保存：

main Compilation → candidate round

因此最重要的层级是：

root Compiler
└── CollectionSession
    ├── main Compilation 1 → round 1
    ├── main Compilation 2 → round 2
    └── committed：最近一次成功发布的规范化结果

不同文件通常是同一个 Compilation 中的不同 Module，并不会各自产生 Compilation。round 的边界是一次主 Compilation，而不是一个文件。

round 的结构是：

round = {
  invocations: 0,
  submissions: Map<identity, snapshot>,
  warnings: Set,
  abandoned: false
}

submit 按 resource identity 替换完整 snapshot；noteInvocation 记录 Loader 确实被调用；warn 按 code + identity 在本轮去重。一个空 snapshot 仍然是有效提交，表示资源当前贡献为空。

3. Loader 的调用链：一次执行同时留下两种状态

Webpack 调用 Loader 时，把本次请求的运行时上下文作为 Loader 函数的 this。项目中的 loaderContext 不是项目创建的，而是 Webpack 创建的临时对象；loaderContext._module、_compilation、_compiler 是 Webpack 内部上下文引用。

loader.pitch / loader
    ↓
runCollect(loaderContext, sourceText)
    ↓
loadConfig → describeResource → collectedFor
    ↓
extractor → publishWarnings → record

record() 是两条状态链的交汇点：

extractor 生成完整 snapshot
    ├── 写入当前 Module 的 buildInfo.i18nCollect
    └── 提交当前 Compilation 的 round

也就是说，项目不是把 metadata 存在 loaderContext 上，而是使用 loaderContext._module 找到当前 Webpack Module，然后写入：

module.buildInfo.i18nCollect = {
  schemaVersion: 1,
  root,
  fileConfigHash,
  invoked: true,
  included,
  snapshot
}

LoaderContext 的 this.data 只用于 pitch 与 normal 阶段之间防止同一次 Loader 调用重复收集；它不是跨 Compilation 的状态。

4. metadata 的生命周期与缓存边界

metadata 是附着在 Module 上的、普通且可序列化的构建状态。它不是 Session 的字段，也不是 round 的字段；round.commit() 或 round.abandon() 不负责回滚它。

Webpack 的 memory cache 或 filesystem cache 命中时，Webpack 可能复用模块构建状态；filesystem cache 还可能把可序列化的 Module 构建状态写入磁盘并在下一次构建恢复。因此，Loader 本轮没有重新执行时，当前 Compilation 的 Module 仍可能带有恢复后的 buildInfo.i18nCollect。

第一次构建：
loaderContext₁ → Module₁.buildInfo.i18nCollect
                         ↓ Webpack cache
第二次构建：
当前 Module（可能复用，也可能是恢复出的新对象）
└── buildInfo.i18nCollect

这里不能说旧的 loaderContext 或旧的 Module 对象必然跨 Compilation 存活。准确说法是：Webpack 可能恢复 Module 的可序列化构建状态；若缓存未命中、状态未被恢复或模块重新构建，metadata 就不存在，Loader 必须在当前构建中重新执行。项目的集成测试覆盖了 filesystem cache 命中且 Loader 执行次数为零的场景。

metadata 的作用不是让未变化模块重新打包，而是让 Plugin 在 Loader 不重跑时仍有机会获得该模块对全量收集结果的贡献。它必须经过 schema、root、fileConfigHash 和 snapshot 结构校验，不能盲信。

5. live set、candidate 与 recovered

Plugin 不扫描业务目录，也不调用 extractor。它从当前 Compilation 的 Module 集合和 Session 的本轮提交中组装候选。

当前 Compilation
├── main modules
│   └── assembleLiveSet(main, context) → live
├── child modules
│   └── assembleLiveSet(child, context) → recovered
└── 当前 round
    └── candidateSnapshots() → submitted

assembleLiveSet(modules, context) 遍历传入的 Module，读取每个 module.buildInfo.i18nCollect，调用 interpretMetadata() 校验，按 identity 去重，并返回：

{
  snapshots,
  integrated,
  diagnostics
}
  • live：主 Compilation 当前 Module graph 中存在且 metadata 合法的 snapshot。它是一次汇总时计算的临时视图，不是长期存储。
  • recovered：child Compilation 的 Module metadata 组装结果，主要解决 HtmlWebpackPlugin 的缓存 child compilation 场景。
  • submitted：当前 round 中 Loader 主动提交的 candidate snapshot。

这不是“先查 round，失败后再查 metadata”。Plugin 同时读取不同来源：普通资源主要依赖主 Module graph 的 live；本轮重跑资源会有 submitted；child compilation 的静态 HTML 还需要特殊恢复。

普通资源如果不在当前 Module graph 中，旧贡献不会因为历史 committed 而永久保留。删除文件、移除 import、删除 Vue block，或 style index/lang 发生变化，都应在成功轮次中淘汰相应旧 identity。

child compilation 的 snapshot 不会全部无条件加入结果。当前实现只对静态 HTML 做特殊处理：确认模板仍是配置模板、仍是依赖、文件存在、scope 通过，并且没有新的 snapshot 覆盖它后，retainStaticHtmlSnapshots() 才会保留它。

6. Plugin 的函数级调用链

Plugin 的主要实现位于 myplugin/index.js。

apply(compiler)
  ├─ getSession(rootCompiler)
  └─ 注册 thisCompilation / afterSeal / done

thisCompilation(compilation)
  └─ session.begin(compilation)

afterSeal
  └─ snapshotsForRelease()
      ├─ separatedModules()
      ├─ assembleLiveSet(main, context)
      ├─ assembleLiveSet(child, context)
      └─ session.candidateSnapshots(compilation)

done(stats)
  ├─ 检查 compilation 错误和 abandoned
  ├─ snapshotsForRelease()
  ├─ loadConfig({ pluginOptions })
  ├─ activeHtmlTemplates()
  ├─ retainStaticHtmlSnapshots()
  ├─ buildCatalog()
  ├─ 检查 key conflict
  └─ session.release(..., writeOutputs)

各函数的职责是：

  • getSession()：按 root Compiler 复用或创建 Session。
  • session.begin()：按主 Compilation 创建本轮 round。
  • separatedModules()：把主 Compilation 与 child Compilation 的 Module 分开。
  • metadataContext()：生成当前 canonical root 与 fileConfigHash，供 metadata 校验。
  • assembleLiveSet()：从给定 Module 集合读取、校验、去重 metadata snapshot。
  • snapshotsForRelease()：汇总 live、recovered、submitted，并合并 diagnostics/integrated 状态。
  • activeHtmlTemplates()：确认 HTMLWebpackPlugin 当前真正活动的模板。
  • retainStaticHtmlSnapshots()：按 active template、live、submitted 和 committed 规则处理静态 HTML。
  • buildCatalog()：把最终 snapshots 转换为目录、hash dictionary 与 source map 所需的聚合数据，并基于 previous catalog metadata 恢复 automatic key；ambiguity 或 key conflict 会阻止发布。
  • session.release()：先 checkpoint/commit 内存状态，再调用输出写入；写失败时 rollback。

7. Plugin 的完整生命周期

root Compiler ↓ getSession CollectionSession ↓ thisCompilation 创建本次 main Compilation 的 round ↓ Loader 执行 Module metadata + round submissions ↓ afterSeal 检查当前 graph、接入证据和 metadata diagnostics ↓ done 重新汇总 live/recovered/submitted ↓ 处理静态 HTML → buildCatalog → 检查 key conflict ↓ session.release ├─ commit + writeOutputs 成功 → committed 与磁盘更新 └─ 任一失败 → abandon/rollback，保留上一成功结果

afterSeal 主要用于尽早发现未接入、metadata 非法或其他诊断；done 才在 compilation 成功后构建最终目录并发布。候选 snapshot 进入 round 或 live set，都不等于已经正式发布。

8. 为什么不能直接把本轮结果当成正式结果？

Loader 提交的是 candidate，不代表整个 Compilation 成功。其他模块可能有语法错误，多个资源可能产生 localization key conflict，或者输出写入可能失败。因此项目保留上一次 committed 状态：

round candidate
    ↓ compilation / catalog 校验通过
session.release()
    ↓ 写出成功
committed + dictionary + source map + catalog

如果构建失败，当前 round 被放弃，上一成功的 committed 和磁盘产物保持不变；identity ambiguity、message-contract key conflict 也属于不能发布的 collection failure。如果写文件中途失败，release() 使用 checkpoint 回滚内存；output.js 使用 journal 保证多文件成组替换能够恢复，避免出现半新半旧的输出。

9. 多轮构建中各量何时变化

量创建/更新边界
Session第一次看到 root Compiler 时创建当前 Node.js 进程和 root Compiler 生命周期
roundthisCompilation → begin；Loader 调用时更新一次 main Compilation；成功 commit 或失败 abandon
metadataLoader 写入当前 Module；Webpack cache 命中时可能恢复Module 构建状态；不由 round 自动回滚
live每次 assembleLiveSet 临时计算当前 Compilation 的 Module graph
submittedsession.submit 写入 round当前 round；同 identity 后提交覆盖前提交
committedrelease 成功后更新，写失败时 rollbackSession 内最近一次整体成功结果

memory cache 只在当前进程和适用的 Compiler/cache 生命周期内可能复用模块状态；filesystem cache 可以在命中且成功反序列化时跨进程恢复可序列化的 Module 构建状态。Session、round、Map、WeakMap 和 LoaderContext 都不是 filesystem cache 的业务持久化替代品。

检索练习

第二次 watch 构建只重新执行了模块 B 的 Loader，而模块 A、C 命中 filesystem cache。请说明 Plugin 如何得到完整结果，以及如果模块 C 已经不再位于当前 Module graph 中会怎样。

模块 B 通过当前 round 提交新 snapshot；A、C 如果由 Webpack cache 恢复了合法 metadata，则由当前 Module graph 的 assembleLiveSet() 读回。Plugin 汇总出 A、最新 B、C。若 C 已经不在当前 Module graph，旧 committed 中的 C 不会被普通资源无条件保留，成功轮次会淘汰 C。
