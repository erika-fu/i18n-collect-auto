一次收集轮次如何安全地成为正式结果

本课把“Loader 提交了快照”到“磁盘出现四组产物”之间的状态变化逐步展开。

1. 一个 compilation 对应一个候选 round

session.js 通过以 root compiler 为键的 WeakMap 隔离不同 compiler。一个 compilation 开始时建立 round，round 只保存本轮候选：

round = {
  invocations: 0,
  submissions: Map<identity, snapshot>,
  warnings: Set,
  abandoned: false
}

submit 按 identity 覆盖同一轮中同一资源的提交；noteInvocation 只记录“Loader 被调用”；warn 按 code + identity 去重 warning。它们分别表达不同事实，不能用“entries 为空”代替 invocation。

2. 为什么要把 snapshot 放进 module metadata

Loader 写入 module.buildInfo.i18nCollect 的是可序列化信封：

{
  schemaVersion: 1,
  root: '/canonical/project',
  fileConfigHash: '...',
  invoked: true,
  included: true,
  snapshot: { identity, projectPath, owner, entries }
}

Webpack filesystem cache 命中时，Loader 可能不重新执行；Plugin 仍可从当前 module graph 的 buildInfo 恢复 snapshot。恢复不是盲信：interpretMetadata 会检查 schema、canonical root 和 fileConfigHash。root 或配置不一致时，metadata 属于另一构建，必须诊断并阻止发布。

3. live set 是什么

最终结果不是“session 里历史上提交过的所有 snapshot”，而是当前 compilation/module graph 中仍存活、metadata 合法的 snapshot 集合：

当前 modules ↓ 读取 buildInfo.i18nCollect 校验 root / schema / config hash ↓ 按 identity 去重 ↓ live snapshots ↓ buildCatalog + dictionary + source map

因此文件移出 module graph、block 被删除或 scope 不再匹配时，旧贡献不会因为“历史提交”永久保留。静态 HTML 是例外中的例外：HWP child compiler 可能命中缓存而不重新调用 Loader，retainStaticHtmlSnapshots 还要确认模板仍是配置模板、仍是依赖、文件存在且在 scope 内。

4. Plugin 的边界与生命周期

MyI18nPlugin 可以读取 compilation/module graph、session metadata 和配置；它不读取业务源码、不调用 extractor。典型顺序是：

thisCompilation → begin round
compilation.hooks.afterSeal → 检查 graph、Loader invocation、metadata
compiler.hooks.done → 构建成功后 assemble/release/write

把解析源码放进 Plugin 会破坏 Loader-owned collection：Plugin 看不到准确的 Loader 语义边界，也会把未参与构建的孤儿文件带进结果。

5. 为什么必须先成功再提交

候选结果只有在 compilation 没有错误、接入证据完整、catalog 没有 key conflict、输出可以成组写入时，才成为 committed state。失败时：

  • round 标记 abandoned；
  • 内存中的上一成功状态保留；
  • 磁盘上的 dictionary、source map、source catalog、metadata 都保持旧版本；
  • 下一次构建重新从当前 graph 产生候选。

这就是“事务式 collection”：不能发布只收集到一半的词典。

6. 多文件输出为什么需要 journal

output.js 先序列化并比较每个目标文件的字节。全部相同则直接返回，不创建临时文件，因此 watch 不会因无意义写入再次触发。

有变化时，流程近似为：

写 journal（记录 final/temp/backup） → 写所有 temp 文件 → 备份旧 final → 逐个 rename temp → final → 全部成功后删除 journal → 任一步失败则按 journal 恢复

如果进程在中途退出，下一次提交先调用 recoverCommits 恢复残留 journal，再读取输出。多文件“最终看起来一致”依赖的是这组记录，而不是希望 rename 恰好都成功。

7. 一个真实的时序限制

应用模块可能在构建早期导入 zh_hash.json，而 Plugin 只有在 compilation 结束后才能写最新 dictionary。因此本次构建的 bundle 可能嵌入旧字典，但磁盘产物已经是新字典；watch 会再触发一次，下一轮消费新字典。项目选择最终收敛，而不是引入双阶段构建。

检索练习

为什么一个 Loader 已经提交了 snapshot，但 compilation 失败后不能直接把它放进 committed store？为什么 output.js 还要单独做 journal？

Loader 提交的是本轮候选，不代表整轮通过；其他模块错误、跨资源 key conflict 或接入诊断都可能使它无效，所以要保留上一成功 committed store。journal 解决的是另一层问题：四类输出文件必须成组更新，任一 rename 中断都能按记录恢复，避免半新半旧。
